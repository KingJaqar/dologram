### 4.2 Authoritative aggregate writes and compatibility

Proposed RPC: `public.mark_chat_read(p_chat_id uuid, p_max_seq bigint, p_membership_joined_at timestamptz) returns setof public.chat_members`, exactly one final own row. The result preserves the existing sender/`.single()` shape; extend the new sender/wrapper arguments to carry the opaque server-issued membership timestamp unchanged. Add shared repository `markChatRead` in `members.ts`; mobile aliases it as `persistChatRead`. Update every sender caller/test and DB types from the isolated schema, preserving unrelated working-copy types. Root `gen:types` has placeholder target arguments; do not run it unchanged.

1. Reject missing `auth.uid()`, missing expected membership and null/negative/out-of-safe-JavaScript-integer input (maximum `9007199254740991`). Lock the current own membership row and compare its server `joined_at` with the submitted identity before any write; mismatch is `DG409`/`membership_changed`, requiring refresh rather than replay against the new membership. This closes the check-to-request race for new clients. Legacy direct UPDATE remains compatible but cannot attest a client membership generation or human viewing intent; do not claim this new request guard exists in old clients.
2. Compute authorized maximum stored message seq for this chat, including tombstones, or 0 for empty history. Clamp request, then take `greatest(old_cursor, clamped_request)`. This bounds new advancement without lowering a cursor after history deletion. Do not assert the old permanent “cursor <= current maximum row” invariant. If baseline data has invalid cursors, report reconciliation needs rather than silently lowering them.
3. Return persisted state for advances/no-ops. Definer function uses fixed empty `search_path`, qualified objects, explicit caller checks and authenticated-only EXECUTE, revoking default PUBLIC/anon access. Definer code must enforce authorization explicitly. Proposed five-character SQLSTATE codes: `DG401` unauthenticated, `DG403` not a member, `DG405` not message author, `DG409` membership changed, `DG422` invalid input. Preserve them through existing `ClassifiedError` server-code fields and map to named UI reasons; do not parse database prose or assume long semantic names are valid SQLSTATE codes.
4. Revoke authenticated table-wide UPDATE; grant only `last_read_seq`, `archived`, `muted_until`, retaining own-row RLS. Preserve nickname RPC. Keep legacy direct read UPDATE through a server BEFORE trigger applying the same validation/clamp/max rules, but narrow the new client's `OwnMemberPatch` to archive/mute after migrating its cursor callers. Narrow authenticated INSERT to existing callers' necessary fields (currently `chat_id`, `user_id`, `role`; confirm every caller in Phase 0), and initialize read cursor 0 so INSERT cannot bypass checks. Do not accidentally disable owner/member creation.
5. In Phase 4 attach one private receipt routine to actual cursor advancement in the same transaction, shared by RPC and legacy UPDATE. No client receipt DML. This corrects “only RPC creates receipts”: older clients need the same server trigger, not a bypass. Do not duplicate insertion in RPC and trigger.
6. Archive/mute/nickname operations must not create read work. Preserve direct-key triggers and owner/member operations; establish consistent lock order and bounded transaction/lock timeouts, including removal/read races.

Proposed migrations: `<next>_harden_chat_read_state.sql` and later `<next>_message_read_receipts.sql`. Choose next zero-padded versions after inspecting working copy and target history; 035–036 already exist, so do not reserve/reuse them or renumber applied versions. Migration 035 also makes blanket private-schema revocation unsafe as a template: use exact new-object grants/revokes and preserve existing helper permissions. Before interpreting new SQL results, establish whether the target inherited that unrelated baseline conflict; do not hide it inside a Seen migration or weaken RLS to make tests pass.

For safe authoritative pruning, also propose `public.get_chat_member_snapshot(p_chat_id uuid)` returning one JSON object with `members` and `total_count` from one consistent authorized database snapshot. Require current membership and use the same restricted definer conventions. A JSON container avoids silently treating a row-capped PostgREST array as the full membership set. Adapt `listChatMembers` internally to validate count/unique IDs/chat identity, valid safe cursors/server membership timestamps and inclusion of the authenticated caller before returning its existing `DgResult<ChatMemberRow[]>`, preserving callers' return contract. ### 4.4 Detailed storage, coverage and retention

**Blocked until Phase 3 closes B-01.** Names are proposed; no guessed privacy defaults may ship.

Add `public.message_read_receipts`: primary key `(message_id, user_id)`; cascade FKs to message/chat/auth user; verified message seq; server `read_at timestamptz`; indexed `expires_at timestamptz`. Copies of chat/seq come from authoritative message and are checked by a private integrity trigger. Use timestamptz directly, without implicit timestamp-without-time-zone conversion. Index `(message_id, read_at, user_id)` for stable queries and expiry for cleanup; a `read_at` index alone does not implement message-age expiry.

On old-to-next cursor advance, atomically insert receipts for other senders' messages in `(old, next]`, excluding deleted/tombstoned, out-of-retention, Saved Messages and over-limit groups. `ON CONFLICT DO NOTHING` preserves first time. Timestamp means **first server-recorded read-through**, including offline acknowledgement after reconnection, not an unobservable offline human viewing instant. Never trust device time or backfill exact time from a cursor. Receipt insertion failure rolls back the advance; retry remains safe.

Use validated server-owned configuration: initial retention 7 days, inclusive group limit 100, recorded collection-start timestamp and a fail-closed detail exposure switch. No new operational-settings UI. Store expiry as message creation plus retention at collection; effective query expiry is the earlier of the durable message collection-window cap below and message creation plus current retention. Decreasing retention hides old details immediately even if cleanup fails; increasing it cannot revive an expired record, restore deleted data or imply historical completeness. For an empty roster, return the message's currently applicable expiry. Hide deleted-message details immediately and clean their receipts without changing cursors.

Enforce that no-revival guarantee with proposed `private.message_read_detail_windows(message_id uuid primary key references public.messages(message_id) on delete cascade, expires_at timestamptz not null)`. The shared atomic receipt routine establishes a message's window on its first eligible collection, using message creation plus the current retention. All later readers use that same non-increasing cap; they cannot establish a longer window by joining or rereading. This metadata has no reader identity or `read_at`, has no client table/function access, and cannot prove who read or supply an exact time. Keep its row until the parent message is hard-deleted, even after all receipts expire or are removed; ordinary receipt cleanup must not delete it. A message with no collection window yet uses current message-age eligibility, and any new window is created only by an actual eligible cursor advance, never a detail query or cursor/time backfill. This makes “prospective increase” precise: new windows may use the new duration; existing windows never extend.

The server-only configuration operation must atomically lower existing window caps and retained receipt `expires_at` values to the new message-age cap and commit the configuration change together. Serialize it with collection/configuration changes so a concurrent insert cannot commit using the old longer policy after the cap. Collection and query both enforce the durable window, including when no receipt rows remain. A later increase leaves existing caps unchanged and never fills gaps. Query-time `min` alone fails before cleanup; receipt-row caps alone fail after cleanup removes them. For example, shorten retention until a three-day-old message expires, delete its receipts, restore seven days, then let a group member leave/rejoin and reread: the window must still block recollection and return `expired`, without recreating a new first-read time. Bound this infrequent configuration transaction; on timeout/failure roll back caps and setting, preserve the old configuration and report the blocker. No partially applied retention change or direct client configuration writes. Test both before- and after-cleanup sequences, concurrent collection and rollback. Include retained window rows/indexes in storage and query-cost measurements; this is receipt eligibility metadata, not a message-expiry engine.

Roster means current other members who have read the sender's outgoing message, matching current-member aggregate semantics. Removed readers are excluded; removed senders cannot query. A retained first account/message receipt across leave/rejoin is shown only when current membership/cursor qualifies, within retention. Actual server count controls size eligibility.

Coverage rules:

- Messages predating collection start return `not_recorded`, even if aggregate Seen is true.
- Query in one consistent snapshot compares current qualifying other-member cursors with stored receipts. A missing required record returns whole-result `not_recorded`, with no misleading partial roster. This handles reads while details were disabled, groups shrinking, configuration changes and mixed versions. Never fabricate missing times.
- Reducing limits hides details immediately; increasing limits cannot turn gaps into empty rosters. `available` with empty participants means genuinely no qualifying other reader, not hidden/expired/gapped history.
