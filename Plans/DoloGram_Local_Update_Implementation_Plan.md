## 1. Goal and scope

Add **Settings → About → Local update** to the Android APK distribution of DoloGram. The user chooses an APK through Android's native file picker, DoloGram checks that it is a newer compatible DoloGram build, and Android presents its installation confirmation.

The feature works without a backend or internet connection when the APK is already stored locally. A document provider backed by cloud storage may still need connectivity to retrieve its file. “Local update” does not search the internet or establish that a selected build is the latest published release.

Initial scope:

- Android only, for the existing direct/internal APK distribution.
- One standalone APK per attempt; no AAB, XAPK, APKM, or split-APK installation.
- Reject another app's package, unreadable archives, incompatible signing identities, and equal/older build codes before opening the installer.
- Keep Android's required user confirmation and unknown-source authorization.
- Preserve existing accounts, messages, queue, preferences, notifications, and storage through an ordinary in-place update.

Automatic downloading, background updates, silent installation, Google Play updates, signing-key rotation support, and iOS installation are outside this implementation. Google Play restricts the installation permission for self-updating apps; a future Play build must omit this feature and permission and use a separate update path. [Google Play installation-permission policy](https://support.google.com/googleplay/android-developer/answer/12085295)

## 3. Selected implementation approach

Reuse Expo DocumentPicker and FileSystem for selection and staging. Add a small **local Android Expo module** for installed-package metadata, candidate APK inspection, unknown-source authorization, and launching the system installer.

The native module is justified by the selected validation requirements: opening an intent alone does not identify the APK's package, signer, or build code. Keep all Android-specific behavior behind a typed adapter so other platforms can import Settings safely. Local Expo modules are supported without abandoning the Expo workflow. [Expo local-module guide](https://docs.expo.dev/modules/get-started/)

Do not add a second intent-launching dependency when the module already provides the required native operations. Do not build a custom installer or implement PackageInstaller sessions for this initial feature; hand the staged APK to Android's installer with a read-granted content URI.

### Native adapter contract

Use the following logical operations; exact Expo export names can follow project conventions:

- `getInstalledInfo()` → actual installed application ID, native version name, and build code as an exact decimal string. Compare native codes as Kotlin Long values; avoid JS floating-point or lexical version comparison.
- `inspectCandidate(stagedFileUri, attemptId)` → native validation result plus candidate version name/build code. Perform parsing off the UI thread and associate completion with that attempt.
- `canRequestInstall()` → current Android install-source authorization.
- `openInstallPermissionSettings(attemptId)` → this app's unknown-source settings screen, subject to the same stale-attempt/dispatch-deadline checks as installer dispatch.
- `invalidateAttempt(attemptId)` → idempotently mark pending native work stale; check this flag and a native dispatch deadline immediately before any queued Activity launch. It cannot cancel an installer already handed off. Expose no fake guarantee that an in-progress PackageManager/disk operation was interrupted.
- `launchInstaller(stagedFileUri, attemptId)` → revalidate the candidate and authorization, obtain its content URI from the existing FileSystem provider, grant read access, and launch Android's installer on the main thread with a foreground Activity. Reject repeated launches for the same attempt. Resolve as **handed off**, never as **installed**.

Use typed errors such as `unreadable`, `invalidApk`, `wrongPackage`, `wrongSigner`, `sameVersion`, `olderVersion`, `permissionRequired`, and `installerUnavailable`. Translate them into shared user-facing strings. Unknown native errors receive a generic retry message without exposing private file paths.

Add `unsupportedApk`, `storageFull`, `operationTimedOut`, and `settingsUnavailable` where required. Use optional native lookup (`requireOptionalNativeModule`, verified in installed Expo Modules Core) and an explicit capability check; iOS/web and Android clients missing this module must not throw during import. Capability is unavailable, not a successful no-op. A supported release missing its module fails the release gate.

## 4. User flow and lifecycle

1. Under About, display the actual installed version/build and a **Local update** row with helper text: “Choose a newer DoloGram APK from this device.” Keep existing non-Android version behavior. On an Android client without the module, preserve the old version fallback and hide the update control; do not claim a metadata-read failure is a native build number.
2. Disable the row while an attempt is in progress or a call is incoming, outgoing, connecting, active, or reconnecting. Also guard a nonterminal current call even if its rendered phase is unavailable. Explain the call restriction with “Finish your call before updating.”
3. Open the system picker with single selection and APK MIME type `application/vnd.android.package-archive`. If it is cancelled, return quietly to idle and offer a contextual, accessible **Browse all files** retry alongside the row's helper; only that explicit tap starts a new `*/*` selection. This gives a concrete recovery when a provider hides APKs due to incorrect MIME metadata without auto-reopening a cancelled picker. Filename and MIME are selection hints, not proof of validity.
4. Use `copyToCacheDirectory: true`. Await moving the readable picker copy into an app-owned `local-updates/<attempt-id>/candidate.apk` cache directory. If a move cannot be used, await a disk copy and clean the extra owned copy after success/failure. Generate the directory name internally; do not use the provider's filename as a path. Only remove a picker file after verifying it is an owned cached copy, never an original/provider file. SDK 57 documents this cache-copy option for immediate FileSystem access. [Expo DocumentPicker](https://docs.expo.dev/versions/v57.0.0/sdk/document-picker/)

   FileSystem 57's awaited copy/move return void, and move changes the source object's URI. Retain the original source URI separately; never delete a moved File wrapper as if it still represented the redundant picker copy. Use the confirmed destination URI for inspection and dispatch. [Expo SDK 57 FileSystem](https://docs.expo.dev/versions/v57.0.0/sdk/filesystem.md)
5. Inspect the staged APK. Surface a specific rejection and return to idle if validation fails.
6. Display a confirmation with installed and selected version/build, filename as display text, and “Android will ask you to confirm the update. DoloGram will close during installation.” Use **Continue** and **Cancel**.
7. On API 26+, if install-source authorization is missing, explain why and offer **Open settings**. Open `ACTION_MANAGE_UNKNOWN_APP_SOURCES` for `package:<installed application ID>`. On return, recheck authorization rather than trusting an activity result. If allowed, restore the confirmation; require another explicit Continue tap. If denied, allow retry or cancel without reopening Settings in a loop. If no settings handler exists, show manual instructions and allow cancellation. API 24–25 have no per-app authorization API: hand off to the installer, let Android enforce the device's global unknown-source setting, and explain that older-device restriction if blocked. Do not call newer APIs there. [Android unknown-source settings](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_UNKNOWN_APP_SOURCES)
8. Immediately before handoff, recheck the current call, ownership/focus, staged file, installed/candidate metadata, and permission. Dismiss the app dialog before launching. The native module constructs the content URI from its validated canonical file using AndroidX FileProvider and the verified `${context.packageName}.FileSystemFileProvider` authority; no caller-supplied arbitrary content URI. Launch once using `ACTION_VIEW`, the APK MIME type, `FLAG_GRANT_READ_URI_PERMISSION`, and ClipData for that same URI. Do not send `file://` URIs or add broad storage/package-query permissions. Catch activity/security exceptions rather than requiring a package-visibility pre-query that could return a false negative. Android FileProvider supports temporary read grants to external activities. [Android FileProvider](https://developer.android.com/reference/androidx/core/content/FileProvider)
9. Android owns the final installation prompt, compatibility checks, and outcome. After a witnessed background-to-foreground transition associated with handoff, return to idle without reporting installed/cancelled/failed as a known result. If that transition was not observed, do not infer completion from a redundant active event or the native promise resolving. A navigation-away/back after handoff may release the UI lock once launch has settled, but retain its file/grant under the retention policy. After replacement, a fresh launch reads the new native version/build. Android may close the app; automatic relaunch is not promised.

State model: `idle → picking → preparing → validating → confirming → permissionSettings / handingOff → awaitingReturn → idle`, with rejection/cancellation returning through cleanup to idle. In `permissionSettings`, a return restores confirmation or the denied-permission explanation. In `awaitingReturn`, retain no promise of an installation outcome. Record whether each external activity actually caused backgrounding, including a fast return before its launch promise settles; do not miss that event or resume twice.

Keep a process-wide single-attempt/operation guard in the update service, plus rendered disabled state and native attempt deduplication. A component-local ref alone is insufficient across unmount/remount. Remove hook listeners on unmount; mark an abandoned pre-handoff attempt invalid and release its guard only when outstanding work settles safely. Capture account identity and invalidate on account change. Use route focus (Expo Router exports useFocusEffect) to distinguish leaving Settings from opening a system activity; backgrounding for the picker/permission screen is expected and is not route cancellation. Ignore stale results and clean only their owned files. Re-read the latest call state before handoff; a rendered closure must not allow a newly incoming call to be missed. Once handed off, Android owns installation and a newly arriving call cannot reliably cancel it; the app never ends calls automatically.

In addition to the final latest-state read, when the controller observes a nonterminal call during **any** pre-dispatch state, invalidate the attempt in JS and native code. That includes a call observed while launch-time archive revalidation is pending. The native main-thread dispatch must recheck invalidation/deadline immediately before startActivity. Account/route invalidation uses the same rule. The observable boundary is the controller's observed eligibility before dispatch; this does not promise atomic exclusion of a call that becomes known only after Android has received the install request.

Do not time out the user's time in picker/Settings/installer UI. For app-owned post-picker staging/inspection, including launch-time archive revalidation, use a proposed 120-second watchdog; metadata/permission queries and final Activity dispatch each have a 10-second bound. The launch method's revalidation and dispatch budgets are separate, with a maximum controller watchdog of 130 seconds; do not accidentally apply a 10-second whole-method timeout to archive parsing. These are failure bounds, not measured performance guarantees. A timed-out promise is not proof that native work stopped: invalidate the generation, prevent late UI/launch side effects, keep operation serialization until it settles, and defer deletion while a file operation could still use it. A dispatch timeout with uncertain side effects retains the file and requires return/reconciliation, never an automatic retry. Test the actual boundary with deferred operations. After two identical failures, diagnose/report rather than looping.

**Verified SDK boundary:** installed DocumentPicker 57 performs its cache copy inside its native activity-result handling, before getDocumentAsync resolves. The post-picker watchdog cannot bound that SDK/provider copy and cannot distinguish it from human picker time. Retain the agreed copyToCacheDirectory setting; make no claim that the app can cancel or time-limit the SDK's pending picker/copy. If it remains unresolved after the external UI has closed, explain that the selection is still pending, keep the shared operation guard, and provide instructions to restart DoloGram if it cannot settle; no automatic restart or second picker. A rejected/in-progress picker gives an actionable message rather than an automatic retry loop. Measure this boundary in V08; report an observed native picker stall as such rather than falsely crediting the app watchdog. No vendor patch or replacement picker is added by this plan.

If the process dies, discard the in-memory attempt and ask the user to choose again; no automatic installation on restart. Android may evict cache files at any time; a missing candidate prompts reselection. No root-layout startup hook is needed: clean expired attempts on supported Settings entry and before the next selection. This assigns cleanup ownership without adding unrelated app startup work.

## 5. Validation, storage, and data rules

### Candidate rules

- Read installed identity from Android PackageManager, not Expo configuration or an APK filename.
- Parse the staged archive with PackageManager and signing information using API-level-compatible flags. Missing package/signing metadata is a rejection. Archive parsing is preflight validation; Android's installer remains responsible for full signature/integrity enforcement. [Android PackageManager](https://developer.android.com/reference/android/content/pm/PackageManager)
- Use `GET_SIGNING_CERTIFICATES`/current `apkContentsSigners` on API 28+, the legacy signatures flag below 28, and the API 33 PackageInfoFlags overload only behind an API 33 guard (the int-flags overload remains usable below). Use longVersionCode on API 28+ and a widened versionCode below. Compare complete signer sets without depending on their order; do not treat any shared historical certificate as proof of the selected strict current-signer policy. [Android SigningInfo](https://developer.android.com/reference/android/content/pm/SigningInfo)
- Require the candidate application ID to match the running app's installed ID (`com.dologram.app` in current configuration).
- For this first version, require matching current signing-certificate sets. Reject absent or different signers, including debug/release mismatches. Supporting valid certificate-rotation lineages is separate work; fail with an explanatory message rather than incorrectly claiming all Android-compatible signing rotations are supported.
- Require candidate native build code to be strictly greater than installed build code. Equal codes get “This build is already installed”; lower codes get “Choose a newer DoloGram build.” Compare numeric build codes, never version-name strings. Android permits equal codes in some update paths, but this product deliberately requires a newer one. [Android update requirements](https://developer.android.com/google/play/app-updates)
- Require one standalone APK. Reject recognizable non-APK containers/split-only archives using actual parsed metadata, not the display name; if PackageManager does not expose enough information to prove a base APK has no required splits, do not invent that guarantee. Treat inability to install a base requiring missing splits as an Android installer rejection. Native fixture tests establish the available detection; final ABI, minimum SDK, policy, storage and completeness enforcement remains Android's responsibility. Merely renaming a ZIP/APKM to .apk must not bypass archive validation.
- Restrict native file access to canonical paths inside this feature's cache directory. Revalidate the same private file immediately before handoff; do not trust arbitrary JS-provided external paths or content URIs.

### Cache and outcome handling

- Do not read APK bytes into JavaScript or encode them as base64. Keep file operations on disk.
- Do not apply chat attachment MIME restrictions or its 50 MB file limit to an APK.
- On picker cancellation, app confirmation cancellation, validation failure, or staging failure, remove only that attempt's owned temporary files. Preserve the user's original APK.
- After handoff, retain the staged file while Android may be reading it. Do not delete it in a launch `finally` block or merely because AppState becomes active.
- On Settings entry/next attempt, clean abandoned attempt directories older than 24 hours, excluding any live operation/handoff; age them from app-owned creation metadata, not the APK's provider modification time. This is a proposed retention window, not an assertion that an installer can never stay open longer. After process death, a recent attempt stays protected for the window; if an exceptionally old external installer loses its file, Android reports failure and the user can reselect. Verify canonical directory ownership before recursive deletion, remove stale non-handed-off copies promptly, and never broadly delete cache. Retention is age-based, not a strict byte cap; repeated attempts/large APKs can exhaust free space. Fail gracefully without deleting younger handoff copies to make room. Revoke a grant when its expired file is safely removed, not immediately after dispatch.
- Record no APK contents, account data, or private file locations in telemetry. Test evidence may record artifact hash, application ID, version code, and public signing-certificate fingerprint.
- Never call sign-out, clearLocalData, queue cleanup, uninstall, or database reset as part of updating. Existing initialization and migrations run normally after replacement.

### 9.3 Retry, recovery, and rollback boundaries

- Before handoff, failed preparation/validation/permission can be cancelled and retried explicitly after safe owned-copy cleanup. Leave the installed app and original APK unchanged. If file cleanup fails, retain a redacted diagnostic and let the scoped expired-attempt sweep retry later; never mask the primary error or broadly delete data.
- After handoff, keep the file/grant until safe expiry and reconcile the actual native version on subsequent app entry. An Android rejection normally leaves the prior build installed; verify that fact rather than assuming it. Never retry an uncertain dispatch automatically.
- A successful replacement cannot be safely rolled back by uninstall/reinstall or choosing a lower code under this feature. Preserve the signing key and issue a corrected APK with a still-higher code if recovery is needed. Use the existing distribution method if the app cannot open Settings. Do not promise recoverable user-data export where no existing mechanism has been verified.
- Restore source-only feature edits from the local snapshots/patches after reconciling concurrent user work; do not reset the working tree or restore secrets from ordinary context. Do not roll back an EAS remote version counter; record gaps and continue with monotonic codes. Process cleanup targets only owned processes/temporary mappings.
